# AREA: achievements-ui
##########################################################################################

## MEASURED
The two UGS scripts are thin PanelRenderer hosts: they construct exactly two Blocks visual elements (`AchievementsContainer` and `AchievementNotificationElement`), assign the static `AchievementBaseElement.Icons` list, and re-parent the element into the PanelRenderer's root on every UIReload callback. That is the entire compile-time surface — three types and one static field. The critical structural finding is that there is NO UXML anywhere in this area: both prefabs carry `sourceAsset: {fileID: 0}` (AchievementsPrefab.prefab:86, AchievementsNotificationPrefab.prefab:101), no `.uxml` in the repo instantiates any `Blocks.Achievements.UI` tag (grepped all `.uxml`; only the editor-only AchievementsInspector.uxml matched "Achievement"), and there is not a single `Q<>()` / `Query()` call in either the Blocks achievements runtime or the UGS achievements scripts. The whole visual tree is built imperatively in C# constructors, so there is zero C#-to-UXML name contract to preserve — the `[UxmlElement]` attributes on the four element classes exist only for UI Builder authoring and are dead at runtime. What IS load-bearing is (a) the USS class-name strings in `AchievementsTheme`/`BlocksTheme` paired against `Common/Content/composites/card-component.uss` and the other theme sheets, and (b) a string contract between the `Icon` field in `Deployment/Achievements.ach` and `Texture2D.name` — `AchievementBaseElement.GetIcon` matches by asset name ("thumbnail", "thumbnail_blue", "thumbnail_green", "thumbnail_red", plus "thumbnail_black" as the not-found fallback), so replacement art must be named identically or the .ach re-authored in lockstep. Class names are therefore free to change (C# and USS are both ours to rewrite); texture asset names and the .ach `Icon` values are a hard pair. Every visual dependency reaches outside this folder into `ThirdParty/Blocks/Common/` (BlocksPanelSettings.asset, BlocksRuntimeTheme.tss with its 13 relative `@import`s, card-component.uss with a relative `url("../textures/thumbnail.png")`), so the achievements panel cannot be made self-contained without also replacing that Common slice.

## APPROACH
The replacement is a five-layer, self-contained achievements stack under `CrawfisSoftware.UGS.Achievements` (+ `.UI`), written against Remote Config / Cloud Save / Cloud Code SDK APIs only, with the Cloud Code path built on `ICloudCodeService.CallModuleEndpointAsync<T>` and locally declared DTOs so `Unity.Services.CloudCode.GeneratedBindings` is never referenced. API compatibility with the four UGS achievement scripts is preserved at the *call-shape* level rather than the type-name level: `new AchievementsContainerElement(useTrustedClient, DevelopmentMode, m_Icons)` keeps the existing two-bool ctor arity with an appended optional icon argument; the property `AchievementsPrefab.AchievementsContainer` and the field `AchievementsNotificationPrefab.AchievementsNotification` keep their names (only their declared types change); the serialized names `InitOnAwake`, `DevelopmentMode`, `UseTrustedClient`, `m_Icons`, `m_UiPanel` are untouched, so `AchievementsPrefab.prefab:106-115` and the `m_Icons.Array.data[0]` scene override at `AchievementNotifications.unity:249` keep binding. Because the measurement proved there is no UXML and no `Q<>()` anywhere in this area (both prefabs carry `sourceAsset: {fileID: 0}`), every element is built imperatively and every class name is free — the only preserved hard runtime contracts are the `Texture2D.name` ↔ Remote Config `Icon` string pair, the Cloud Save key `"achievements"` with its `Id`/`Unlocked`/`ProgressCount` JSON keys, the Remote Config key `"achievements"` with the `AchievementDefinition` field names, and the five MonoBehaviour serialized field names. Three fragilities are designed out rather than reproduced: the public static mutable `AchievementBaseElement.Icons` becomes a per-service `AchievementIconLibrary` whose `Register` *merges* by texture name (first writer wins) so neither panel can wipe the other's icons; the notification's `TransitionEndEvent` state machine becomes a `schedule.Execute` timeline so a stylesheet without a transition cannot strand the toast in `Showing`; and the never-unsubscribed `AchievementUnlocked` handler becomes an `AttachToPanelEvent`/`DetachFromPanelEvent` pair. The service also replaces the three `ServiceObserver` dances with the repo's own `ServiceObserverHelpers` plus a `UGS_EventsEnum.PlayerAuthenticated`/`PlayerSignedIn` bus subscription, and publishes `AchievementUnlocked`, `AchievementProgressUpdated` and the `AchievementClaiming`/`Claimed`/`ClaimFailed` triple on `UGSBus`, so consumers stop reaching for a C# event on a singleton. Styling is a single new `achievements.uss` with `ugs-`-prefixed original class names and **zero `url()` references** — the card thumbnail is set only from C# via `style.backgroundImage`, which deletes the `../textures/thumbnail.png` relative-path taint at `card-component.uss:50` outright. No new PanelSettings is needed: `Assets/UGS/UI/UGS Panel Settings.asset` (guid `4c8011be1283eb042ad4a0e7a6f30d4a`) is already ours and byte-identical to `BlocksPanelSettings`, so both prefabs are repointed to it with a one-token guid swap.

## MEASURED
The Blocks achievements service layer is a self-contained 8-file runtime (753 lines) plus a 9-file editor tooling set for the `.ach` Remote Config deployment file. UGS consumes only a four-member slice of it: `AchievementsObserver.Instance`, `.UnlockAchievementAsync(string)`, `.AchievementUnlocked`, and `.RuntimeAchievementData.Achievements` (plus `Achievement.Id`) — all from `CoinBasedAchievements.cs` and `DistanceBasedAchievements.cs`. The critical GeneratedBindings question has a cleaner answer than expected: all four Achievements-area dependencies on `Unity.Services.CloudCode.GeneratedBindings` are reachable ONLY through `TrustedAchievementClient`, and the shipping scenes never construct it — `Assets/UGS/Prefabs/UGS/AchievementsPrefab.prefab:108` sets `UseTrustedClient: 0`, that prefab field is the only value that ever reaches `AchievementsObserver.UseTrustedClient` (via `AchievementsPrefab.cs:114` -> `AchievementsContainer.cs:42`), and no scene overrides it. So the achievements replacement drops the Cloud Code path entirely and needs zero `CallModuleEndpointAsync` rewriting; the shipping path is `LocalAchievementClient` = Remote Config (definitions) + Cloud Save (records). Should the trusted path ever be wanted back, it is a trivial port: the generated `AchievementClientBindings` is nothing but four wrappers over `ICloudCodeService.CallModuleEndpointAsync<T>("BlocksGameModule", "<fn>", args)`, and the three generated model POCOs have field-for-field identical shapes to the Blocks models, so `CallModuleEndpointAsync<List<Achievement>>` would deserialize straight into our own types with no adapter. Much of the observer skeleton is already duplicated in original repo code: `Assets/UGS/Scripts/RemoteConfig/DifficultyObserver.cs` is a near-line-for-line reimplementation of `AchievementsObserver`'s singleton + `ServiceObserver<IAuthenticationService>` + SignedIn + `FetchConfigsAsync` structure, and `ServiceObserverHelpers.cs:19` even carries a TODO naming Blocks as the source. `Achievements.ach` is a Remote Config deployment file (key `achievements`, type JSON) defining nine ids including `first_achievement`; nothing reads it at runtime — the runtime reads the deployed Remote Config key instead. Two premise corrections worth carrying up: Blocks is NOT the sole GeneratedBindings consumer (five live UGS files import it for TempleRunUGSCloud, and `CrawfisSoftware.UGS.asmdef:14` references the assembly), and `CoinBasedAchievements.cs` is referenced by no scene, prefab or asset at all.

## APPROACH
The replacement is a nine-file runtime under `CrawfisSoftware.UGS.Achievements` — deliberately the SAME namespace the four consumer scripts already declare, so no consumer gains a `using` line, only an identifier rename. `AchievementsObserver` becomes `AchievementsService`, a lazy singleton built on `ServiceObserverHelpers.InitializeServiceObserver<IAuthenticationService>` (`Assets/UGS/Scripts/RemoteConfig/ServiceObserverHelpers.cs:20`) — the exact skeleton already written as original repo code in `DifficultyObserver.cs:51-112`, whose `// Todo` at ServiceObserverHelpers.cs:19 this closes. `RuntimeAchievementData` becomes `AchievementCatalog`, keeping `IDataSourceViewHashProvider` + `INotifyBindablePropertyChanged` (both verified present in `6000.5.7f1/Editor/Data/Managed/UnityEngine/UnityEngine.UIElementsModule.dll`) and the exact member names `Achievements`, `propertyChanged`, `GetViewHashCode`, because the UI area binds to those. `TrustedAchievementClient` is deleted outright, which removes all four `Unity.Services.CloudCode.GeneratedBindings` imports in this area by deletion; the trusted path is re-provided as an original `CloudCodeAchievementRepository` written against `CloudCodeService.Instance.CallModuleEndpointAsync<T>` with DTOs I declare, whose module and function names come from a `CloudCodeAchievementOptions` object that ships **unconfigured** — so the package names no Cloud Code module it does not own, and `AchievementsService.UseTrustedClient` keeps its name and meaning, costing `AchievementsPrefab.cs:114` and the prefab's `UseTrustedClient: 0` field zero edits. `LocalAchievementClient` becomes `CloudSaveAchievementRepository`, and this is where the design deliberately diverges: definitions are read from `RemoteConfigService.Instance.appConfig.GetJson("achievements","[]")` (the boot fetch at `RemoteConfigManager.cs:87` already has it) with a `FetchConfigsAsync` fallback and a `DifficultyObserver.cs:119-122`-style null guard, dropping a network round trip and the hard throw on a missing key; and records are round-tripped through Cloud Save with the write-lock token (`Item.WriteLock` → `new SaveItem(json, writeLock)`, bounded retry on `CloudSaveConflictException`), which fixes the lost-update race that `LocalAchievementClient.cs:103-121` inherits. The repository interface is id-based for mutations (`UnlockAsync(string) -> AchievementRecord`) and the *service* merges the returned state into the `AchievementRecord` instance the UI is already bound to via `CopyStateFrom`, instead of swapping `Achievement.Record` for a freshly deserialized object as `LocalAchievementClient.cs:107/123` does — that is the aliasing fix, and it is why `AchievementRecord.Changed` now actually reaches the bound card. The service raises the same `event Action<Achievement> AchievementUnlocked` the notification element needs AND publishes `UGS_EventsEnum.AchievementUnlocked` / `AchievementProgressUpdated` / a new `AchievementsFetched` on `UGSBus`, which lets `DistanceBasedAchievements` replace its never-unsubscribed `Awake()` lambda (lines 33-36) with a bus subscribe/unsubscribe pair and satisfy the repo's own rule. Finally the editor tooling is reimplemented on Unity's own `RemoteConfigImporter<TAsset,TFile>` / `RemoteConfigAsset` bases (`Library/PackageCache/com.unity.remote-config@1ad1930762f4/Editor/Authoring/Assets/`) under a NEW extension `.ugsach`, which sidesteps the global `[ScriptedImporter(1,"ach")]` collision with a consumer-installed Building Blocks; the Deployment window still finds it because `RemoteConfigDeploymentProvider.cs:18` enumerates by type (`ObservableAssets<RemoteConfigAsset>`), not by extension — verified.

## APPROACH
Delete the Blocks leaderboard stack outright and rebuild it as five original C# files plus three text assets under the package root (today `Assets/UGS/`, which becomes the package root since `Assets/UGS/CrawfisSoftware.UGS.asmdef` already sits there). The 499 lines of observer/client/data plumbing collapse into one stateless static facade, `LeaderboardQuery`, that makes exactly three calls on `Unity.Services.Leaderboards.ILeaderboardsService` (GetScoresAsync / GetScoresByTierAsync / GetPlayerRangeAsync — signatures verified in Library/PackageCache/com.unity.services.leaderboards@4afe9822e038/Runtime/Unity.Services.Leaderboards.api:82,84,80) and translates `LeaderboardsException.Reason` into a log plus an empty list instead of throwing; there is no singleton, no ServiceObserver, no ILeaderboardsClient, no Unity.Properties binding model, and no Cloud Code path at all, so `Unity.Services.CloudCode.GeneratedBindings` is never touched. The display is a `PanelRenderer`-hosted element tree — `LeaderboardPanel` (MonoBehaviour) → `LeaderboardView` (built-in `TabView` with a Global and a Player tab) → `LeaderboardList` (built-in `ListView` + an explicit status Label) → `LeaderboardRow` (three Labels) — matching the PanelRenderer pattern already proven at Assets/UGS/Scripts/Achievements/AchievementsPrefab.cs:39-143 and retiring the last `UIDocument` in the repo. The critical design move is that ALL styling ships as two `StyleSheet` references serialized on the prefab and added with `root.styleSheets.Add(...)`, with every design token declared on a `.ugs-panel` class selector rather than `:root`: this removes the entire `@import` chain that the measurement identified as the hardest part, so a mis-resolved relative path can no longer silently blank the panel, and the panel styles correctly no matter which PanelSettings the host scene uses. `Assets/UGS/UI/UGS Panel Settings.asset:15` still needs its `themeUss` repointed off the deleted `BlocksRuntimeTheme.tss` (guid 2e74663645b63fe43ad48957a2398ce5) to a new one-line `UgsRuntimeTheme.tss` that only does `@import url("unity-theme://default")`, which is what gives `TabView`/`ListView`/`ScrollView` their built-in look — and that edit is pure text because the `themeUss` fileID `-4733365628477956816` is a constant of the .tss ScriptedImporter (verified identical across Assets/Settings/GUI/PS_Menu.asset:15 → MenuTheme.tss guid b886c2221727a64478707961a5a3f7b1 and Assets/UGS/UI/UGS Panel Settings.asset:15 → BlocksRuntimeTheme.tss). API compatibility is trivially satisfied because our code consumed only two property setters: `LeaderboardsObserver.Instance.LeaderboardId` and `.UseTrustedClient` at Assets/UGS/Scripts/Leaderboard/LeaderboardPlayerController.cs:30-31, both of which are pure deletions — the observer's LeaderboardId only drove the Blocks display, which we now drive from the panel's own serialized `_leaderboardId`, and UseTrustedClient never took effect anyway (the prefab still serialises the pre-rename `m_UseServerAuthority: 0` at Assets/UGS/ThirdParty/Blocks/Leaderboards/Prefabs/LeaderboardPrefab.prefab:50, so the trusted client was never built). Score submission is untouched: it already bypasses Blocks at LeaderboardPlayerController.cs:73. Refresh timing is improved rather than copied — the panel refreshes on `UGS_EventsEnum.LeaderboardOpened` (published by LeaderboardController.cs:75 after the additive scene load) and again on `ScoreUpdated`, so the list can no longer render before the player's own new score has landed, and a generation counter plus a `CancellationTokenSource` cancelled in `OnDestroy` stops a late await from touching VisualElements in an unloaded scene.

## DESIGN RISKS
  [medium] Design tokens are declared on a `.ugs-panel` class selector and attached with root.styleSheets.Add(), not on `:root` in the PanelSettings theme. This is the bet that removes the measurement's 'hardest part' — but if Unity's var() resolution from a non-root ancestor misbehaves in 6000.5.7f1, EVERY leaderboard rule falls back to its initial value and the panel renders as unstyled grey boxes. It fails silently and cannot be caught by compiling.
      -> This is precisely what step (b) of the play-mode pass checks, and it is a one-glance verdict. Fallback if it misbehaves: move the token block from UgsPanel.uss into UgsRuntimeTheme.tss under `:root` and add `@import url("UgsPanel.uss")` there — a relative import inside our own package folder, which moves with the package (unlike the Blocks theme's imports, which broke only because files were moved out from under them). The rest of the design is unaffected either way, because Leaderboard.uss stays attached via styleSheets.Add() regardless of where the tokens live.
  [high] PREMISE CORRECTION, and it is the biggest packaging risk on this whole plan: deleting Blocks does NOT free the package from Unity.Services.CloudCode.GeneratedBindings. That asmdef at Assets/CloudCode/GeneratedModuleBindings/ also holds the project's OWN TempleRunUGSCloud bindings, and five non-Blocks UGS files import the namespace (PlayerEconomyManagerClient.cs:7, PlayerEconomyManager.cs:6, PlayerDataManagerClient.cs:10, PlayerDataManager.cs:8, LocalStorageSystem.cs:10). Assets/UGS/CrawfisSoftware.UGS.asmdef therefore keeps its `Unity.Services.CloudCode.GeneratedBindings` reference to an assembly living in the consumer's Assets/ — which a package cannot do.
      -> Out of scope for leaderboards, and this area contributes what it can: severing TrustedLeaderboardClient.cs removes LeaderboardClientBindings' only consumer. The residual problem belongs to the Economy/PlayerData areas — the generated bindings must move into or beside the package, or be replaced by explicit request/response types over CloudCodeService.Instance.CallModuleEndpointAsync<T>. Confirm with that owner before the packaging plan is finalised; do not let the leaderboard work be reported as having closed this gap.
  [medium] The prefab and scene YAML are hand-authored. A malformed block, a duplicated fileID, or a serialized field name that does not match LeaderboardPanel.cs exactly produces a silently null reference (e.g. _panel unassigned -> NullReferenceException in OnEnable) or a component Unity drops on import, with no compile error.
      -> Copy the component skeleton verbatim from the already-working Assets/UGS/Prefabs/UGS/AchievementsPrefab.prefab:1-93 rather than writing PanelRenderer YAML from scratch — it is the same component, the same Unity version, and the same PanelRenderer-with-no-UXML shape. Add a `if (_panel == null) { Debug.LogError(...); enabled = false; return; }` guard in Awake so a mis-wired prefab reports itself instead of spraying NREs.
  [medium] Async completion after the leaderboard scene unloads. The Leaderboards scene is loaded additively on LeaderboardOpening and destroyed on LeaderboardClosed (CloseSceneOnEvent, Leaderboards.unity:152) roughly 5s later; the 2.3.4 SDK accepts no CancellationToken, so an in-flight GetScoresAsync WILL complete after OnDestroy and its continuation will touch VisualElements belonging to a dead panel. The Blocks version had the same exposure.
      -> Three layers, all in LeaderboardPanel: a CancellationTokenSource cancelled and disposed in OnDestroy; a monotonically increasing _generation captured before the await and compared after (a stale result is dropped, which also makes the three refresh triggers safe to overlap); and a `if (this == null) return;` Unity-null check immediately after each await before touching any element. Step (g) of the play-mode pass is what confirms it.
  [medium] The `_tier` value being migrated is `weekly_distance_tier_1` (UGS_Boot_4_Leaderboards.unity:169) while the leaderboard id is `DailyDistance`. If someone carries that value across into LeaderboardPanel._tierId, GetScoresByTierAsync raises LeaderboardsExceptionReason.TierNotFound and the global tab shows the empty message for every player — a regression dressed up as 'implementing the unfinished field'.
      -> Ship the new prefab with `_tierId:` EMPTY, which routes to GetTopScoresAsync and reproduces today's working behaviour exactly. LeaderboardQuery already logs TierNotFound as an error including both ids, so the mistake is one console line away from diagnosis.
  [low] LeaderboardPanel subscribes in Awake() and depends on UGS_EventsEnum.LeaderboardOpened (published by LeaderboardController.cs:75 from the SceneManager.sceneLoaded callback) arriving after that Awake. For an additive LoadSceneAsync, Unity runs the new scene's Awake/OnEnable before firing sceneLoaded and before any Start — so the ordering holds — but it is an ordering assumption about another object's callback, not a guarantee this code controls.
      -> Belt and braces: _refreshOnStart (default true) fires an independent refresh in Start(), which runs strictly after sceneLoaded. ## MEASURED
The sign-in feature is a PanelRenderer showing Assets/UGS/UI/PlayerAccountLogin.uxml, whose only interactive content is one fully-qualified custom tag `<Blocks.PlayerAccount.PlayerSignIn/>` (PlayerAccountLogin.uxml:6). PlayerSignIn is a self-constructing VisualElement that builds three buttons (Sign in Anonymously / Sign in with Unity / Sign in with Password) and owns a CloudDataContainer that makes the actual UGS calls; the password path lazily adds a second element, PlayerSignUpOrSignInWithPassword. Our own C#, Assets/UGS/Scripts/Authentication/PlayerSignInController.cs, consumes exactly two Blocks types: `AuthenticationObserver` (constructed at :32, one method called at :134) and `PlayerSignIn` (a typed `root.Q<PlayerSignIn>()` at :73 that is used only to add/remove a CSS class). The controller never subscribes to a Blocks event and never publishes anything the block raises — completion is reported by the SDK's own `Unity.Services.Authentication.Components.PlayerAuthentication` component in UGS_Boot_2_Authentication.unity:348-439, whose `SignedIn` UnityEvent calls `UnityEventsToEventsPublisher.SignedIn` which publishes `UGS_EventsEnum.PlayerSignedIn`. So the block is pure UI plus three direct SDK calls; nothing in the event architecture depends on it. Critically, `AuthenticationObserver`'s base class `ServiceObserver<T>` is NOT Blocks content — it is public API from com.unity.services.core (Library/PackageCache/com.unity.services.core@3464cb68d709/Runtime/Core/ServiceObserver.cs:10), so the observer is a 25-line re-write, not a re-invention. The genuine risk is threefold and entirely non-compiling: the UXML tag string, the `Style src` on PlayerAccountLogin.uxml:3 pointing into the Blocks tree by absolute project:// URI + GUID, and PS_Login.asset:15 whose `themeUss` GUID resolves to Assets/UGS/ThirdParty/Blocks/Common/BlocksRuntimeTheme.tss. Additionally, the CSS class `.hidden` — which PlayerSignInController.cs:24 and PlayerSignIn.cs:19 both depend on — is defined in exactly one place in the whole repo: Assets/UGS/ThirdParty/Blocks/PlayerAccount/Scripts/Runtime/UI/PlayerAccountStyle.uss:148.

## APPROACH
The area splits cleanly into three original layers, none of which needs Blocks. (1) A service layer: `AuthenticationObserver` is rewritten as a ~70-line class that COMPOSES `Unity.Services.Core.ServiceObserver<IAuthenticationService>` (verified public package API at Library/PackageCache/com.unity.services.core@3464cb68d709/Runtime/Core/ServiceObserver.cs:10) instead of deriving from it, and internally reuses our own existing `ServiceObserverHelpers.InitializeServiceObserver<T>` (Assets/UGS/Scripts/RemoteConfig/ServiceObserverHelpers.cs:20), whose fire-once-on-initialize pattern is already proven in this repo. Composition is safe because PlayerSignInController.cs consumes only two members — `new AuthenticationObserver()` (:32) and `RegisterSignedInCallback(Action)` (:134) — and never touches the base's `Service`/`Initialized`/`Dispose`; composition buys us a real `Dispose()` that also detaches a pending `IAuthenticationService.SignedIn` hook, fixing the leak the measurement flagged. (2) `CloudDataContainer` is NOT ported: its data-binding half (IDataSourceViewHashProvider / INotifyBindablePropertyChanged / [CreateProperty]) and its entire CloudSave half are unreachable from the login panel, so it is replaced by a ~170-line `PlayerSignInService` that owns nothing but the observer and makes four SDK calls directly — `SignInAnonymouslyAsync` (IAuthenticationService.cs:153), `PlayerAccountService.StartSignInAsync` + `SignedIn`/`SignInFailed` + `AccessToken` → `SignInWithUnityAsync` (IAuthenticationService.cs:825, IPlayerAccountService.cs:15/26/31/62), `SignInWithUsernamePasswordAsync` (:893) and `SignUpWithUsernamePasswordAsync` (:915). Every method returns `Task<bool>` and never throws for an expected auth failure — it raises a `SignInFailed(string)` event that the panel renders, which is exactly the upstream bug (a swallowed exception making the in-UI error label unreachable) inverted into working behaviour; the raw AccessToken is never logged. (3) A UI layer: `PlayerSignIn` becomes a `[UxmlElement] public partial class` in namespace `CrawfisSoftware.UGS.Authentication` — deliberately the SAME namespace as its only consumer, so the entire C# cost in the six Blocks-dependent scripts is deleting `using Blocks.PlayerAccount;` from PlayerSignInController.cs:1, a one-line diff, with the typed `root.Q<PlayerSignIn>()` at :73 continuing to compile untouched. The element builds its service lazily on `AttachToPanelEvent` guarded by `Application.isPlaying` and disposes it on `DetachFromPanelEvent`, so nothing UGS-related is constructed during UXML import or in UI Builder. The password sub-flow is kept for visual parity but moved into a non-`[UxmlElement]` `PasswordSignInForm` styled by a CLASS rather than a type selector, removing the silently-breakable `PlayerSignUpOrSignInWithPassword` type selector at PlayerAccountStyle.uss:56, and it is gated behind a `password-enabled` UXML attribute so a project without a Username/Password identity provider can turn it off without a code change. Styling is re-authored as three original text files (`UgsRuntimeTheme.tss` + `UgsTokens.uss` + `UgsControls.uss`) plus edits to our own `PlayerAccountLogin.uss`; because `fileID: -4733365628477956816` is verified to be the universal ThemeStyleSheet main-object id for every .tss in this project (Assets/Settings/GUI/PS_*.asset:15, Assets/UGS/UI/*.asset:15, and four package-cache PanelSettings), repointing PS_Login.asset is a pure GUID swap on one line with the fileID unchanged, so its own guid 097332d7a39dc7848947505b553aa666 / fileID 11400000 survive and the scene reference at UGS_Boot_2_Authentication.unity:218 is untouched. The `<Style src>` at PlayerAccountLogin.uxml:3 pointing into the Blocks tree is DELETED rather than repointed — the sign-in layout rules move into PlayerAccountLogin.uss, which the UXML already imports at line 2 — which eliminates the hand-written project:// URI entirely rather than hand-editing a second one. Nothing in this area touches Unity.Services.CloudCode.GeneratedBindings (verified: every consumer lives under Assets/CloudCode/GeneratedModuleBindings/, outside the CrawfisSoftware.UGS asmdef), so no CallModuleEndpointAsync design is needed here, and the replacement publishes nothing on the event bus — completion continues to flow from the SDK's own PlayerAuthentication component through UnityEventsToEventsPublisher.SignedIn (Assets/UGS/Scripts/Initialization/UnityEventsToEventsPublisher.cs:25-28).

        /// IAuthenticationService.SignInWithUnityAsync. Both handlers are detached in a finally block.
        /// The access token is NEVER logged. Cancelling the token abandons the wait and returns false.
        /// </summary>
        public System.Threading.Tasks.Task<bool> SignInWithUnityAccountAsync(

        /// <summary>Username/password sign-in. Requires a Username-Password identity provider in the dashboard.</summary>

        /// </summary>
        public System.Threading.Tasks.Task<bool> SignUpWithPasswordAsync(
            string username, string password,
            System.Threading.CancellationToken cancellationToken = default);
    
        /// <summary>Cancels any in-flight wait and disposes the observer if this instance owns it.</summary>
        public void Dispose();

## MEASURED
The whole visual identity of the UGS UI is one 26-line theme file, `Assets/UGS/ThirdParty/Blocks/Common/BlocksRuntimeTheme.tss`, which does `@import url("unity-theme://default")` (line 1) then pulls in 13 relative USS files (lines 3-15) totalling 763 lines / 114 rule blocks. ## APPROACH
The whole theme layer collapses from 16 Blocks files (1 .tss + 13 .uss + 3 PanelSettings + 6 textures) into 6 text files plus 5 original PNGs, all authored as text, with zero `url()` asset references anywhere in the USS — which eliminates the 29-relative-path fragility outright. The new theme is `UgsRuntimeTheme.tss`, which does `@import url("unity-theme://default")` (never the `/Assets/UI Toolkit/...` absolute form that `Assets/GameFlow/UI Toolkit/UI/USS/MenuTheme.tss:1` uses, since that cannot resolve from a package) and then imports three siblings **in the same folder**, so every import is a bare filename with no `../` hops: `UgsCore.uss` (design tokens, the global `*` reset, `.hidden`), `UgsControls.uss` (button/label/header/textfield/scroll-view/progress-bar/modal), and `UgsComponents.uss` (achievement card, toast, grid, leaderboard row, tab bar). A fourth sheet, `UgsSignIn.uss`, is loaded by GUID from `Assets/UGS/UI/PlayerAccountLogin.uxml` rather than through the theme, exactly as `PlayerAccountStyle.uss` is today, and it absorbs the only two live rules of `Assets/UGS/UI/PlayerAccountLogin.uss` so that file and its `<Style src>` line can both be deleted. The 114 rule blocks become ~48: `icons.uss`, `copy-session--header.uss`, `list-view.uss`, the whole `.blocks-toggle`/`.unity-base-dropdown__*` group, and the 16 CloudDataContainer rules in `PlayerAccountStyle.uss` are dropped because nothing instantiates them. Three PanelSettings collapse to one `UgsPanelSettings.asset`: `Assets/UGS/UI/PS_Login.asset`, `Assets/UGS/UI/UGS Panel Settings.asset` and `Common/BlocksPanelSettings.asset` are byte-identical apart from `m_Name`, and per-panel draw order is already a *component* property — `PanelRenderer` is Renderer-derived and carries its own `m_SortingOrder` (verified 0 / 1 / 0 / 0 at `AchievementsPrefab.prefab:82`, `AchievementsNotificationPrefab.prefab:97`, `LeaderboardPrefab.prefab:66`, `UGS_Boot_2_Authentication.unity:215`), so nothing is lost by sharing one settings asset. API compatibility is preserved on the two axes that break silently: the class literal `"hidden"` (`PlayerSignInController.cs:24`) keeps its exact name and is defined in *both* `UgsCore.uss` and `UgsSignIn.uss`, and the five achievement icons keep their exact filenames (`thumbnail`, `thumbnail_blue`, `thumbnail_green`, `thumbnail_red`, `thumbnail_black`) because `AchievementBaseElement.GetIcon` matches `Texture2D.name` against the `Icon` strings at `Achievements.ach:7,15,23,31,39,47,55,63,71`, which are deployed server-side to Remote Config. Every other Blocks class name is renamed to a `ugs-` prefix and re-exported from one static `CrawfisSoftware.UGS.UI.UgsUiTheme` that subsumes all four Blocks `*Theme.cs` files — and because the grep shows none of the six Blocks-dependent UGS scripts ever reference `BlocksTheme`, `AchievementsTheme`, `LeaderboardsTheme` or `PlayerAccountTheme`, this area forces **zero** edits to those six scripts.

## MEASURED
`CrawfisSoftware.UGS.Editor` is 9 C# files / 418 lines of vendored Blocks code (namespace `Blocks.Achievements.Editor[.UI]`) that exists for exactly one purpose: give `Achievements.ach` a custom inspector with Apply/Revert and a "View in Deployment Window" button. `AchievementsAssetImporter.cs:7` claims the `ach` extension and produces a `RemoteConfigAsset` ScriptableObject — but it adds nothing of its own; the entire import is inherited from `RemoteConfigImporter<TAsset,TFile>` in com.unity.remote-config. The decisive finding for the packaging decision is in `LocalAchievementClient.cs:55-60` and cloud-code `AchievementApi.cs:177-180`: at runtime, achievement definitions are fetched from **Remote Config** under the key `achievements` — never from the `.ach` file. Nothing in the project references the imported `.ach` ScriptableObject by GUID (only its own `.meta`), so the file is 100% an editor/deployment artifact that is excluded from player builds. The prior finding about path computation is CONFIRMED and worse than described: `RemoteConfigImporter.cs:26-28` builds an absolute path as `Path.Join(Application.dataPath.Replace("Assets",""), ctx.assetPath)`, which resolves only for assets physically under `<project>/Assets` or `<project>/Packages`; from a registry/git-installed package the path points at a directory that does not exist, `AchievementsAsset.LoadAchievements` silently yields an empty list (`AchievementsAsset.cs:59,76-79`), and `SaveToDisk` returns `true` even after catching the write exception (`AchievementsAsset.cs:103-109`), so the inspector clears its dirty flag and reports success. Three separate authoring packages are load-bearing here (com.unity.remote-config 4.2.5 for `.ach`, com.unity.services.tooling 1.4.1 for `.ac`, com.unity.services.deployment 1.7.2 + deployment.api 1.1.3 for `.ddef`), all editor-only, and a fourth (com.unity.nuget.newtonsoft-json) arrives transitively. Because the authoring format is an editor-only concern whose only job is to land JSON in Remote Config, a plain ScriptableObject plus a ~40-line "Export to .ach" menu item is strictly better for a package: it is original code, it has no ScriptedImporter extension to collide over, and it works identically from `Packages/`.

## APPROACH
The decisive new fact: `.ach` is a Blocks invention, not a Unity format. `com.unity.remote-config`'s own importer claims `.rc` and only `.rc` (`Library/PackageCache/com.unity.remote-config@1ad1930762f4/Editor/Authoring/Model/FileExtensions.cs:6` — `SupportedExtensions => new string[] {".rc"}`), and the only thing that made `.ach` a Deployment item is `AchievementsAssetImporter.cs:7`. So exporting `.ach` after deleting Blocks would produce a file the Deployment window cannot see. The design therefore exports `.rc`, whose envelope is byte-shape-identical (`Editor/Authoring/Model/Template/new_remote_config.rc.txt` vs `Assets/UGS/ThirdParty/Blocks/Achievements/Deployment/Achievements.ach:1-4,79-81` — same `$schema` URL, same `entries`/`types` keys), which lets the package register no ScriptedImporter at all: no extension to collide over with the real Asset Store package, and no fork of the broken `Path.Join(Application.dataPath.Replace("Assets",""), ctx.assetPath)` logic at `RemoteConfigImporter.cs:26-28`. The replacement is three C# files: a `[Serializable] AchievementDefinition` in the runtime assembly stripped of its `ClientDefinition` ctor (`AchievementDefinition.cs:4,49-57` — the sole GeneratedBindings contamination path into the editor assembly), an `AchievementCatalog` ScriptableObject the consumer creates in their own project, and a static `AchievementCatalogExporter` that hand-writes the JSON envelope. Serialization uses `JsonUtility` only (import maps `entries.achievements` onto `List<AchievementDefinition>` because the six public field names are literally the JSON keys), so the editor assembly's reference list collapses from four entries to one — `CrawfisSoftware.UGS` — dropping `Unity.Services.DeploymentApi`, `Unity.Services.RemoteConfig.Authoring.Editor` and `Unity.Services.RemoteConfig.Editor.Authoring.Core`, and adding no Newtonsoft dependency. Path resolution uses `UnityEditor.FileUtil.GetPhysicalPath` (first-party precedent: `com.unity.burst/Runtime/Editor/BurstLoader.cs:158`, `com.unity.inputsystem/.../EditorHelpers.cs:132`), which correctly maps virtual `Packages/<name>/...` paths through the AssetDatabase and is the direct antidote to the measured bug. Because the catalog `.asset` lives in the CONSUMER's project rather than the package, the export target is derived from `AssetDatabase.GetAssetPath(catalog)` and never from the package's own location, which is exactly the deployment-handoff problem the measurement flagged as hardest. API compatibility is total for the six Blocks-dependent UGS scripts: none of them references anything in the editor assembly, and neither `DistanceBasedAchievements.cs` nor `CoinBasedAchievements.cs` names `AchievementDefinition` at all (they go through `AchievementsObserver`), so my area's only cost to them is a `using` line each — and that line is already being changed by the runtime-achievements area. The inspector is built entirely in C# with UI Toolkit elements, so this area introduces zero `.uxml` and zero `.uss`; `AchievementsInspector.uxml` is deleted rather than repointed because it is located by an `AssetDatabase.FindAssets` name search at `AchievementsAssetInspector.cs:70-76`, not by GUID, so nothing external breaks.
